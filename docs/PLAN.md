# Решение трека Plata: судья, который сам выводит правила эксперта

Рабочая папка решения — этот форк. Исходные материалы анализа: `../analysis/` (отчёты Astra и Argon, ручной судья на правилах), `../prep/` (FAQ, планы). Контракт задачи — `README.md` в корне.

## 1. Что именно мы сдаём

Не список правил, а **процедуру**, которая по размеченному train сама находит правила эксперта, проверяет их и объясняет жюри. Ручные правила из `../analysis/` — это (а) библиотека шаблонов проверок, которые процедура умеет инстанцировать из данных, и (б) контроль: процедура обязана заново найти их на публичном train без подсказок.

Формула успеха: `10 × macro_topic_accuracy + 0.4 × I`, где I — пять бинарных критериев объяснения. Поэтому объяснение рендерится из того же файла, которым пользуется `eval` (критерий 5).

## 2. Архитектура

```
adapt (train.jsonl) ─┐
  1 facts.py        : context → FactSheet (ожидаемые числа, «ядовитые» числа, даты, флаги, по темам)
  2 checkers.py     : библиотека ШАБЛОНОВ проверок (параметризуемых), применимых к (FactSheet, conversation)
  3 hypothesize.py  : для каждого bad: ближайший good-близнец по context + FactSheet → LLM → 1–2 атомарные гипотезы
  4 cluster.py      : гипотезы темы → ≤12 канонических кандидатов; каждый привязан к шаблону проверки или к LLM-предикату
  5 verify.py       : каждый кандидат на ВСЁМ train: TP (пойманные bad), FP (сломанные good)
                      FP=0, TP≥1 → принят (hard); FP>0 → LLM сужает формулировку по контрпримерам, повтор ≤2;
                      не сузилось → в раздел «границы разметки» (allowlist)
  6 manifest        : rules_spec.json — единственный источник истины (правила, приоритеты, примеры-ссылки, allowlist, промпт)
  7 explain.py      : explanation.md из манифеста по 5 критериям жюри
  8 selfcheck       : честная оценка на grouped-split train (не на public test) → в explanation как «внутренняя проверка»
                     └→ /artifacts

eval (test.jsonl + /artifacts) ─┐
  facts.py → детерминированные проверки активных правил → если нарушение: bad
  иначе LLM-судья (открытая модель) с правилами темы + allowlist + 3 ближайших примера из train → good|bad
  LLM недоступен → детерминированный вердикт + пометка в логе (не в predictions.csv)
                     └→ /output/predictions.csv  (item_id,label; ровно одна строка на ID)
```

Любое нарушение применимого правила → `bad` (как в README). Правила действуют в рамках темы.

## 3. FactSheet по темам (шаг 1, чистый код)

| Тема | Ожидаемые величины | «Ядовитые» величины (их появление как итога → нарушение) |
|---|---|---|
| spending | 3 последних полных месяца до `today`; прошлый месяц = M−1; `purchases − refunds` помесячно и среднее; `transfers_to_others` отдельно; суммы по мерчанту/категории из `transactions` с учётом refund | сумма с `transfers_own`; покупки без вычета refunds при refunds>0; цифры текущего неполного месяца в ответе на «прошлый месяц» |
| financial_position | `own_gross` = Σ балансов своих счетов; `available_now` = balance − on_hold; `net_after_debt` = own − current_debt; `Ahorro Fijo` недоступен до maturity | own + available_credit / credit_limit |
| savings | ставка по `plus_subscription` из `savings_rates`; балансы; maturity_date | ставка противоположного тарифа; «изменённый» баланс после «выполненного» перевода |
| credit | все поля `credit_statement`: due_date, next_cut_off_date, no_interest_payment, minimum_payment, total_debt, paid_this_period, msi_plans | даты/суммы, не совпадающие с выпиской |
| общие | язык реплик; какие поля известны из context; числа, названные ассистентом в каждом ходе | число, изменившееся между ходами без причины |

Сравнение чисел: нормализация форматов (`21,617`, `21 617`, `21617.00`, `21.6k` не поддерживаем), допуск округления ±1 и ±0.5%.

## 4. Шаблоны проверок (шаг 2)

1. `poison_number_present(kind)` — в ответе есть ядовитое число как итог.
2. `required_number_missing(kind)` — при условии (on_hold>0, current_debt>0, refunds>0, transfers_to_others>0) обязательное число не названо.
3. `asks_known_field(field)` — ассистент просит у пользователя значение, которое есть в context (паттерны «пришлите/подтвердите/уточните сумму/баланс/подписку/дату»).
4. `denies_known_field(field)` — «не вижу дату/сумму», а поле есть.
5. `wrong_period(kind)` — ответ о прошлом месяце цифрами текущего; «среднее» по 1 месяцу.
6. `rate_mismatch` — ставка не по тарифу.
7. `turn_contradiction` — число/дата из context в одном ходе верны, в другом заменены.
8. `llm_predicate(text)` — семантика: «утверждает, что действие выполнено», «утверждает, что Fijo можно снять досрочно», «что минимальный платёж избавляет от процентов», «соглашается с неверным утверждением пользователя». Проверяется открытой моделью, вход — FactSheet + диалог, выход — JSON `{violated: bool, quote}`.

Новое правило приватного набора, которое ни под один шаблон не ложится, становится `llm_predicate` с формулировкой, выведенной на шаге 3–5, и попадает в судью только после проверки точности на train.

## 5. Allowlist (не нарушения; в explanation — раздел «границы»)

Две конвенции трат (переводы другим внутри итога или отдельной строкой); две конвенции on_hold («собственные» до/после удержания при названной сумме); простые и сложные проценты; таргеты ссылок `lnk_*`; опечатки; одиночный непереведённый анкор; трактовка процентов на остаток сверх беспроцентного платежа (в train оба варианта `good`). Allowlist тоже выводится из данных (кандидаты с FP>0 после сужения) и подтверждается парами item_id.

## 6. Содержимое `/artifacts`

- `rules_spec.json` — правила: id, тема, условие применимости, условие нарушения, тип проверки (шаблон+параметры или llm_predicate), приоритет, TP/FP на train, item_id примеров (bad) и контрпримеров (good), статус (active / boundary).
- `fewshot_index.json` — для каждого train-примера: тема, краткий FactSheet, метка; для kNN в eval.
- `judge_prompt.txt` — системный промпт судьи, отрендеренный из манифеста.
- `explanation.md` — для жюри: критерии; приоритеты (hard-код → hard-LLM → …); ссылки на примеры с цитатами; границы с парами; раздел «как это используется в eval» со ссылками на поля манифеста; внутренняя проверка (grouped split).
- `run_meta.json` — модель, язык, версии, время.

## 7. Модели (решение после исследования Opus / Codex Sol / Astra, 12:45)

- Самое уязвимое место — индукция правил в `adapt`. Туда нужна самая сильная **открытая** модель с доступным endpoint: по умолчанию `openai/gpt-oss-120b` через OpenRouter (structured outputs, reasoning). Альтернатива — `gemma-4-31b-it` (не 26B), если хотим трек Gemma; выбирается переменной `INDUCTION_MODEL`.
- `eval`: та же модель или более дешёвая открытая (`EVAL_MODEL`); модель отвечает только на узкие вопросы да/нет/неизвестно по одному правилу с цитатой, числа считает код.
- Закрытые модели (Claude/GPT) — только за флагом и только после письменного «да» организаторов; все трое исследователей считают, что «закрытый adapt» нельзя честно назвать вспомогательной ролью.
- Кэш ответов по хэшу `(model, rule_id, item_id, prompt)` в `/artifacts/cache/`. Отказ API: 3 повтора, затем детерминированные правила + метка большинства по теме из train; каждый ID получает метку, факт fallback — в stderr/лог.
- Открытый вопрос организаторам: есть ли сеть у контейнеров и чьи ключи; обязателен ли open-weight для трека Plata.

## 7a. Уточнения после исследования

- **Параметризованные семейства, а не жёсткие правила.** «Что считать тратами», «удержания», «долг», «ставка Plus», «период» реализуются с вариантами; вариант выбирается по согласию с train (например, «проверили 4 трактовки, эксперт согласен с X в 37 из 40»). Ни одно публичное правило не включается без повторного отбора на новом train.
- **Новые правила ищутся на остатках без списка известных типов**: модель получает контрастные пары из диалогов, которые текущие правила объясняют неверно, и может предложить произвольный смысловой критерий или новый вычислимый признак. Иначе adapt лишь переоткроет наши шаблоны.
- **Генерируемый код — только в ограниченном DSL** (сравнения над полями FactSheet и утверждениями ассистента), не произвольный Python.
- **Принятие правила:** precision ≥ 0.9, поддержка ≥ 3 диалога из разных контекстов, не ухудшает accuracy ни в одной теме; один раунд сужения по контрпримерам, затем в boundary.
- **Честная оценка:** grouped split (группа = почти одинаковый context); индукция повторяется внутри каждого фолда. Public test — один раз в конце, как регрессия; 1.0 на нём ничего не доказывает.
- **Leave-one-rule-out:** отключить одно известное семейство, запустить adapt, проверить, что оно найдено заново. Это прямая симуляция приватного набора; результат — в explanation и README.
- **Объяснение — детерминированный шаблон из манифеста**, без свободного пересказа моделью; в тексте хэш манифеста и таблица прогона на train. Один балл I стоит столько же, сколько 4 п.п. accuracy.
- Семантические правила возвращают `yes / no / unknown` + цитата; `unknown` не превращается в `good` автоматически, а решается приоритетом по манифесту.

## 8. Проверки честности

- Public test не участвует в adapt. Внутренняя проверка — grouped split train (группа = одинаковый context).
- Контроль «процедура находит правила сама»: прогнать adapt на public train без библиотеки ручных правил → сравнить с `../analysis/astra/rules.json`.
- Контроль «новое правило»: спрятать одно известное семейство из библиотеки шаблонов, прогнать adapt → оно должно появиться как llm_predicate. Пометить в README как синтетический тест.
